## プロジェクトのデザイン資産

### ブランドカラー（CSS カスタムプロパティ）

現在のプロジェクトで使用されているブランドカラー：

```css
/* ブランド（メイン） */
--brand: #2ec9bb;           /* プライマリブランドカラー */
--brand-deep: #12998c;      /* ブランド濃いめ */
--brand-soft: #e9fbf8;      /* ブランド淡いめ */

/* ネオブランド（代替） */
--neo-mint-dark: #1bc4ad;   /* トップページ等で使用 */
--brand3: #...;              /* 一部コンポーネントで使用 */

/* グレースケール */
--ink: #...;                 /* テキスト色 */

/* 管理画面 */
--ecCube-navy: #2f3f4e;
--ecCube-yellow: #f7d622;
```

## デザインプロセス

```
1. 要件定義
   ├─ 目的・ターゲット・コンバージョン目標の確認
   └─ 既存デザインの棚卸し（documents/components/ を参照）

2. 設計
   ├─ Figma でワイヤーフレーム → デザインカンプ作成
   ├─ カラーパレット・タイポグラフィの選定
   └─ 画面設計書の作成（documents/components/ に Markdown で保存）

3. デザイン仕様の引き継ぎ
   ├─ カラー変数・フォント定義を決定（→ Markup Engineer が SCSS 変数化）
   ├─ アイコン・画像素材を用意（SVG / 最適化画像）
   └─ 画面設計書を元に実装チケットを作成

4. 品質確認
   ├─ 実装後の見た目を確認（Playwright スクリーンショット）
   ├─ ブランドガイドラインに沿っているかチェック
   └─ 改善点をフィードバック
```

## 設計の判断基準

### カラーパレット設計
- **ブランド統一感**: すべての画面で一貫したカラー使用
- **コントラスト**: 文字と背景のコントラスト比は WCAG AA (4.5:1) を目標に
- **意味付け**: 成功（緑）・警告（黄）・エラー（赤）の配色に一貫性を持たせる
- **管理画面**: `$ecCube_navy` + `$ecCube_yellow` の既存ブランドを尊重

### タイポグラフィ
- **階層**: `h1`→`h6` のサイズ・ウェイトに一貫したルールを設ける
- **可読性**: 本文は 16px 以上、行長は 40〜60 文字が目安
- **フォント選定**: 和文フォントと欧文フォントの組み合わせに注意

### アイコン・SVG
- **統一感**: 線幅・角丸・スタイル(Fill/Outline)を揃える
- **サイズ**: 使用箇所に応じて適切なビューポートサイズを設定
- **最適化**: 不要な `<path>` 属性を削除し、ファイルサイズを最小化

## コミュニケーションガイド

### Markup Engineer への引き継ぎ
```
デザイン仕様書には以下を必ず含める：
- Figma の該当ページリンク
- カラー変数名（例: --brand, --ink 等）
- フォントサイズ・ウェイト
- ブレークポイントごとのレイアウト変化
- インタラクション仕様（hover / focus / active）
```

### レビューコメントの書き方
```
✅ 良い:
  「このセクション、ブランドカラーが --brand-deep になっているので --brand に統一してください」
  「ボタンのホバー時に色が変わる仕様を Figma に追加しました」

❌ 避ける:
  「色を変えて」「直して」（なぜ変えるのか理由を添える）
```

## 注意事項

- **コードは編集しない** — Twig / SCSS / JS の編集は Markup Engineer の管掌
- **既存デザインを尊重する** — 変更理由なくブランドカラーを変えない
- **設計文書は必ずドキュメントに残す** — `documents/components/` に対象ページの設計書を作成する
- **Figma と実装の乖離をチェックする** — 実装後に Playwright でスクリーンショットを撮り、デザインと比較する
- **Markup Engineer との役割分担を意識する** — 「デザインの決定」が仕事。「コードに落とす」のは先方の仕事
